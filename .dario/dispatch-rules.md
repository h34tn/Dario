# 分派规则

主控按下面的规则决定每一步交给哪个角色。约定的正文在 SPEC.md，本文件只管"怎么拆、交给谁"。

## 交给谁

- 要动手的工作交给"执行者"：`src/` 与 `tests/` 的改动、随改动同步的 `SPEC.md` 与 `README.md`，以及批量检查、日志归纳、样本整理、文档初稿。
- 验证由"测试者"包揽。凡是改了 `src/` 的计划，在执行步骤之后安排一步交给"测试者"：写明这次改动的契约（`SPEC.md` 的哪几节、预期行为），由它补上缺少的测试、运行全量验证并把问题修到通过。怎么测由它决定，任务说明里不要规定具体做法，也不要讲解实现。只改文档或注释的计划不需要这一步。
- 只读的分析、方案评估、检查改动：交给"审核者"。

## 怎么拆

- 一步只动一层。跨层的任务按依赖顺序拆：先 `src/plugin.ts` 与 `src/core/`，再 `src/agents/`、`src/channels/`，最后 `src/cli/`、`src/ui/`。测试与文档跟着所属的那一步走，不单独成步。
- 一步只做一件事，能一步做完的不要拆成多步。
- 每一步的任务说明要写明：涉及哪一层、哪些文件，动手前要读 `SPEC.md` 的哪几节，验收标准，要跑哪些验证命令。
- 改了文件的计划会在最后自动追加一次审核，不必专门安排。只有需要审核重点关注某些方面时，才单独安排一步交给"审核者"并写明要求。

## 不要直接安排编码的情况

下面四类改动会影响已有的使用者、插件或安全边界，必须先给人过目拍板。计划里只安排一步"出设计方案"（交给"审核者"，只读），在结论里请发起人确认；确认后由发起人另行下达实现任务。

- 改插件接口（`src/plugin.ts` 的 `AgentPlugin`、活动类型、接口版本号）或声明式插件清单的格式。
- 改配置文件的格式（项目级与用户级的任何一个 YAML）或两层配置的划分。
- 改给脚本用的稳定接口：JSON 输出的字段、退出码、纯文本输出的格式、子命令与选项的含义。
- 改安全相关的行为：各家 AI 的权限参数、默认放行的工具、环境变量名单、隔离执行策略、渠道的鉴权。

## 任务范围之外

任务由各角色自己做完，计划里不安排要人中途介入的步骤，也不把哪一步留给人。下面这些不在任务范围之内，不要安排步骤；任务涉及到时在结论里写明，结果出来后由发起人决定：

- 提交、推送、发布。
- 安装或升级依赖，改 `package.json`、各 `tsconfig`、`vitest.config.ts`。
- `npm run build`。
- 要在真实终端里用眼睛看的验证（颜色、符号、闪烁、拖动窗口、中文输入法），以及要用真实 AI 额度或真实账号的验证（`dario health`、真实的飞书连接）：角色做不了，如实列为"未验证"。
